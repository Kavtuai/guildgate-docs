# Writing standard

A GuildGate document should help the reader complete a task correctly or understand a behavioral boundary. It must not conflict with source code or the published package surface.

## Source order

Before making a claim, use this order:

1. Published TypeScript declarations
2. Relevant source implementation
3. Tests and contract files
4. Migration or operating-limits documentation
5. Release verification record

When a README example differs from a declaration, use the declaration and passing tests. When documentation and code disagree, verify behavior before updating the text.

## Sentence structure

- Use active verbs: “Compare the origin against the allowlist.”
- State the condition directly: “Production rejects an HTTP origin.”
- Make behavior measurable: “Replay returns at most 500 events.”
- Keep one primary decision in each paragraph.
- Use one term consistently for the same concept.
- Remove unnecessary praise and promotional phrasing.

## Keep boundaries visible

An example should state where it applies:

- memory stores are for development and tests
- a load result is not a production-capacity commitment
- outbox delivery is at least once
- a timeout cannot forcibly stop an arbitrary promise
- atomicity in a custom store belongs to the application

When documenting success behavior, include the failure and recovery path.

## Code examples

- Use a public import path.
- Use the real API name and option shape.
- Use environment variables for secrets.
- Do not hide a security decision behind `any` or an invented helper.
- Add the correct code-fence language and a file title when useful.
- Typecheck examples when possible, or at minimum run a syntax check.

```ts title="config.ts"
const gate = createGuildGate({
  app: {
    name: "Dashboard",
    environment: "production",
    baseUrl: "https://dashboard.example.com",
  },
  // ...
});
```

## Turkish and English parity

Across both locales:

- document IDs must match
- heading structures should correspond
- code examples must show the same behavior
- versions, counts, and limits must match
- a security warning added in one locale must appear in the other

Preserve the same technical meaning rather than translating word by word.

## Headings and emphasis

Headings should describe the decision a reader is looking for. Do not split a short passage into too many sections. Avoid bolding every sentence; use a table only when it improves comparison.

## Links and references

- Verify internal links during the build.
- Open external links and confirm they support the claim.
- Remove temporary tracking parameters.
- Do not invent pages, versions, or source identifiers.
- Give changing numerical results with a date and version.

## Release-note rule

Release notes should state:

- changed behavior
- user or adapter impact
- required migration step
- verification result

Use separate, concise items. Do not publish internal work logs or failed command attempts as release notes.

## Check commands

```bash
npm run search:index
npm run editorial:check
npm run source:check
npm run command:check
npm run site:check
npm run build
```

Fix the file instead of silencing a check. When an exception is necessary, document the reason for a narrow file and marker in source code.

## Review list

- Does the API name exist in the installed version?
- Does the example use a public export path?
- Are version and contract markers correct?
- Is the security boundary explicit?
- Are success and failure behavior separated?
- Do Turkish and English carry the same information?
- Do search title and description match likely user queries?
